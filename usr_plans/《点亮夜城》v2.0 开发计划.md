# 《点亮夜城》v2.0 开发计划

项目仓库：https://github.com/daydream0521/light_up_the_city

## 1. 开发目标

在现有 v1.0 基础上完成一次增量升级，不推倒重做。

v1.0 已经具备完整的 Four-Level 解谜流程、Three.js 程序化城市、美术风格、光路计算、本地存档和 Qoder Sites 公网部署。

本次升级要解决三个问题：

1. 原有四关难度过低，缺少足够的思考与策略。
2. 城市虽然有较好的夜景氛围，但建筑和街区结构重复、缺乏生命力。
3. 通关后没有足够的再次游玩理由，也缺少玩家创作内容的能力。

**产品目标：让《点亮夜城》从一次性视觉 Demo，变成具有解谜深度、创作能力和重复游玩价值的轻量 3D 游戏。**

## 2. 开发原则

- 延续现有夜景美术风格、色彩系统和主要交互方式。
- 复用现有 Three.js 场景、光路逻辑、关卡系统和存档代码。
- 优先实现真实可玩的机制，不为增加功能而增加功能。
- 人类确定目标、体验和验收要求；Agent 自主决定架构、实现细节、技术方案与开发顺序。
- 每个阶段自行完成实现、运行、测试和必要的修复，不需要逐步征求确认。
- 不依赖额外付费 API、玩家登录或外部游戏服务器才能完成核心流程。
- 以有限 Qoder Credits 为约束，优先复用现有代码和美术资产。
- 保留 v1.0 可运行版本，v2.0 验收后再更新公网部署。

## Phase A：玩法系统与关卡设计（P0）

**建议模型：Qwen4-Max**

### A1. 扩展光学机制

保留现有镜面反射机制，增加：

**分光器**

- 一束光可以分成两条路径。
- 分光后能够同时激活不同目标。
- 两条路径应当在画面上明确可辨。

**能量机制**

- 光源拥有有限的初始能量。
- 光线经过反射或分光后，根据明确规则消耗能量。
- 不同目标可以具有不同的能量需求。
- 只有满足目标所需能量才算成功供电。

新规则必须可解释、可预测，玩家应当能够看出当前光线为什么成功或失败。

不要同时加入大量未经验证的新机关。

### A2. 重新设计主线关卡

主线升级为约 8 关：

| 章节 | 核心机制           | 设计目标                       |
| ---- | ------------------ | ------------------------------ |
| 1–2  | 基础反射和路径选择 | 快速上手，建立规则认知         |
| 3–4  | 分光、多目标       | 开始需要综合规划               |
| 5–6  | 能量损耗和路线优化 | 存在不同解法与资源权衡         |
| 7–8  | 综合机关           | 需要完整推理，不靠随意点击通关 |

每关有明确的目标、可行解法和逐渐增加的难度。

教学关保持简短，中后期关卡要有足够的推理空间，不通过无意义增加镜面数量拖延时间。

建议主线首次完整游玩时长约 8–15 分钟；评委应当在开始的 1–2 分钟内体验到具有代表性的玩法和视觉反馈。

### A3. 增加挑战评价

玩家成功通关后，根据操作次数和能量利用情况给出评价。

首先保证不同解法确实存在优劣，不为固定唯一解的关卡强行添加无意义评分。

记录玩家的个人最佳成绩，并允许重玩指定关卡。

### A4. 阶段验收

- 新旧光路机制正确。
- 8 关均可独立完成，没有初始即通关的关卡。
- 分光、能量与目标状态在 3D 场景中正确同步。
- 完成实际浏览器试玩，确保后期关卡确实具有挑战性。
- 旧版基本功能没有被破坏。

## Phase B：玩家关卡编辑器（P0）

**建议模型：Qwen4-Max**

### B1. 关卡编辑功能

在游戏首页增加「创造关卡」入口。

玩家进入编辑器后，可以在固定范围的网格中设计谜题。

至少支持：

- 放置、移动、删除光源。
- 放置、旋转镜面。
- 放置分光器和障碍物。
- 放置一个或多个目标建筑。
- 调整必要的能量参数。
- 输入关卡名称。
- 撤销、清空、试玩、保存。

编辑器与正式游戏复用同一套光路计算与场景渲染逻辑，确保设计画面和实际游玩结果一致。

关卡编辑不包括自由建模、改变建筑外形或自由制作整个城市。

### B2. 试玩与发布

关卡保存前必须能够进入试玩模式。

试玩成功后允许标记为已验证关卡并生成分享链接；未经通关验证的草稿仍可本地保存和继续编辑。

从分享链接打开时，直接进入对应的自制关卡，完成后可以选择重玩或进入编辑器修改自己的副本。

### B3. 本地存档

玩家可以创建多个关卡，并在「我的关卡」页面查看、重命名、编辑、删除和试玩。

使用浏览器本地存储保存草稿和成品，刷新网页后不应丢失。

### B4. 分享机制

必须支持无登录、无数据库的关卡链接分享。

推荐将必要的关卡配置编码到 URL 中，通过访问链接还原关卡；实现方式由 Agent 自主决定。

对导入的关卡数据进行必要的格式和规模限制，避免异常数据导致游戏崩溃或无法渲染。

### B5. Qoder Sites 在线保存

先实际确认当前账号和站点是否支持 Qoder Sites 的数据库及访问者数据写入。

若支持可靠的公开读写能力，在不增加额外付费服务的前提下，尝试增加：

- 保存已验证关卡到服务端。
- 使用关卡 ID 打开分享内容。
- 浏览其他玩家公开发布的关卡。
- 必要的内容长度、数量和访问权限限制。

若当前套餐或站点能力不支持，则保留本地保存及 URL 分享，不使用前端假数据模拟在线存储，也不为此另建复杂后端。

### B6. 阶段验收

完成「创建 → 试玩 → 保存 → 分享 → 其他浏览器打开 → 通关」闭环。

确保玩家无需阅读复杂说明即可理解编辑器主要操作。

## Phase C：美术与城市复苏（P1）

**建议模型：Kimi K3.1 Pro**

这是本次升级最适合使用高成本模型的阶段。

### C1. 保留并强化现有风格

保留深蓝雨夜、金色窗灯、青色光束和微缩城市的整体视觉语言。

不要大规模更换配色、镜头风格或基础场景架构。

### C2. 提升城市建筑多样性

现有建筑以重复的长方体和随机高度变化为主，需要增加结构差异。

至少形成以下几种具有明显轮廓区别的建筑：

- 低层住宅与密集窗户。
- 高层商业建筑。
- 有独特屋顶或轮廓的标志性建筑。
- 桥梁或临水建筑。
- 城市公共设施。

各街区应当具有不同的空间布局和辨识度，避免仅靠高度与颜色变化区分建筑。

暂不引入真实城市地图数据或完整 GIS 系统。

### C3. 城市复苏反馈

玩家通关后，不只是当前建筑的灯光亮起。

根据街区类型增加不同的生活反馈，例如：

- 住宅区灯光依次亮起，出现窗内活动剪影。
- 商业区招牌、广告灯带开始运转。
- 交通区域恢复车辆灯光和移动。
- 江岸或桥梁附近出现灯光、水面反射和活动。

最终全城点亮时，不同街区应形成有层次的灯光演出。

以上可以使用程序化动画和简化的视觉表现，不要求开发完整 NPC 系统。

### C4. 视觉自评

每完成重要场景修改，用真实浏览器从固定视角截图。

从画面层次、建筑辨识度、灯光、镜头构图和视觉噪声等方面进行评价，并根据实际截图修正。

重点保障解谜元素始终清晰可辨，不能因为过度使用 Bloom、雨雾或粒子而影响操作。

### C5. 阶段验收

- 不同街区视觉差异明显。
- 城市完成状态具有明显的生活感。
- 场景从黑暗到复苏的变化具有足够的视觉冲击。
- 视觉升级不影响既有玩法。
- 桌面端正常运行，移动端保留基本可玩性。

## Phase D：每日挑战、整合与发布（P1）

**建议模型：Qwen4-Max**

### D1. 每日挑战

增加独立于主线的「每日挑战」入口。

首版使用若干预先设计、验证可解的挑战关卡，根据日期确定当天的关卡。

同一天所有玩家看到相同谜题。

记录当日完成状态、历史最佳成绩及连续完成天数。

不要求排行榜、账号或云端同步。

每日挑战与普通主线关卡、玩家自制关卡使用一致的光路规则。

### D2. 首页与关卡入口

保留现有首页的美术设计。

使玩家能够直观进入：

- 主线故事
- 每日挑战
- 创造关卡
- 我的关卡

避免堆积多个说明弹窗，入口清晰即可。

### D3. 整合测试

重点检查：

- 主线完整通关与再次挑战。
- 分光、能量、评分正确性。
- 关卡编辑、试玩、保存、分享、导入。
- 本地存档及刷新恢复。
- 每日挑战的日期切换。
- 桌面与移动端基本交互。
- 场景性能、资源释放与浏览器错误。

只针对实际存在的核心行为与高风险边界保留必要测试，不引入与需求无关的测试框架或基础设施。

### D4. 发布

完成测试后使用 Qoder 更新原有 Qoder Sites 网站，保持公开访问。

保留 v1.0 稳定版本的恢复能力。

交付：

- 完整源码及 Git 提交。
- 更新后的 README。
- 新增玩法与编辑器使用说明。
- 关键功能的真实浏览器截图。
- Qoder Sites 公网链接。
- 已完成内容、实际测试结果及未完成限制。

## 3. 不属于 v2.0 的范围

本轮明确不开发：

- 真实城市地图重建。
- 完整开放世界。
- 自由建筑编辑器。
- 多人实时协作。
- 复杂 AI NPC 或对话系统。
- 复杂用户账户、竞技排行榜和社交系统。
- 无限制随机生成的关卡。
- 为了缩小文件体积进行极端代码压缩。

这些内容可在 v2.0 体验完成后，再决定是否进入 v3.0。

## 4. Agent 执行方式

采用自主开发模式。允许 Agent 根据现有代码组织具体实施顺序，对各阶段自行测试、修复和迭代。

以上四个 Phase 是任务边界，不要求每完成一个小功能都向用户确认。

优先级顺序：

**玩法成立 → 玩家可创作分享 → 城市复苏 → 每日挑战 → 额外视觉润色。**

若积分或开发成本不足，应先确保已完成阶段完整可用，不以半成品功能取代现有稳定版本。

特别要求：不要把四个 Phase 全部交给 Kimi 一次性执行。本计划会根据模型费用分配给不同模型，Agent 不应自行扩大高成本模型的使用范围。
